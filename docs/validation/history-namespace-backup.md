# Operational historical namespace backup and restore

The operational CH package now includes all published 028 history manifests and their immutable raw/hourly/daily/vitals rows, streamed into per-manifest NDJSON files in pages of 100. It also streams a PostgreSQL 033 backing fingerprint (published run metadata, effects, original vital samples and relational hour references). The PostgreSQL custom dump taken from the same exported snapshot supplies the actual backing tables. Every package file is SHA-256 checked, fsynced and private; neither application keys nor service credentials are included in this package.

Restore requires a new PostgreSQL database and an explicit, nonexistent `baize_restore_*` ClickHouse database. Existing CH databases are refused. Each archived manifest receives a fresh ID and namespace; its source body checksums are verified before it becomes published in target PostgreSQL. The target PostgreSQL backing fingerprint must exactly match the package. Source namespaces are read only. The current independent deletion journal must extend the package's verified journal prefix. Target startup replays that latest journal, physically removes the precise visitor/identity intervals, rebases surviving historical and relational metadata, enforces current history retention, and rebuilds retained analytics before reporting success. The shell rechecks the live source journal immediately before writing its success marker. A changed journal fails the attempt and retains the isolated target for diagnosis.

Supported package schema is explicitly `028+031+033-through-035+036-empty+037`. Migration 036 currently holds independent, unactivated carry work. Empty 036 tables are supported; any carry checkpoint/key/head/contribution row rejects backup rather than silently omit a future carry state. Unknown later migrations and query versions also reject. Carry activation will require a new tested package contract.

Actual native operational entry validation used separate PostgreSQL databases, a real exported snapshot with `pg_dump`/`pg_restore`, and a fresh ClickHouse database on the existing local test server. It verified source canonical A+B remained unchanged; target canonical and historical raw contained only B after the latest A identity-interval deletion; source historical checksums and namespace remained unchanged; the 033 backing fingerprint matched; existing CH targets, tampered historical files and unknown future schemas were rejected. A real worker SQL failure rejected success; repairing the isolated target and rerunning actually recovered. Final process EXIT 0 is recorded in `/tmp/baize-canonical-history-entry-cleanup-real.log`; the subsequent enhanced entry records include unknown-schema/tamper checks. Earlier failures, including unsupported nonempty future scope and a cleanup force-drop race, remain in the local logs.

The signed standalone history backup now carries bounded 033 backing; its three-file PostgreSQL/ClickHouse regression suite passed 15 tests, including a real deletion-lock wait and the updated precise history-retention assertions. Production Docker shell-wrapper validation still requires the integrator's newly frozen image and resource gate. This local same-server independent database exercise does not establish another-host disaster recovery or provider/runtime CI execution.
