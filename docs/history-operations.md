# Optional historical replica operations

Enable `HISTORY_STORE_ENABLED=1` only with the existing configured ClickHouse connection. It is explicit opt-in; PostgreSQL remains authoritative. No environment configuration is changed by this documentation. Application startup initializes the history table and installs deletion/journal/privacy barriers before serving routes. A configured unreachable history store fails closed; disabling it does not permit deletion to bypass published historical replicas.

Site administrators use `/api/v1/sites/:siteId/storage/history` and its capture/backup/restore routes. A capture preserves original hourly/daily/vitals JSON and retained sanitized events, with per-date SHA256 checksums. Raw detail before retention is unavailable, not reconstructed from aggregates. Signed backup files stay in the private application data volume; API responses omit file paths. Restore requires the latest independently preserved deletion journal, valid signature/site/epoch and an isolated namespace; it does not switch canonical reads or remove PG data.

Maintenance retries failed partial uploads and expires snapshots whose raw rows fall outside site retention. The entire old replica snapshot is invalidated; PostgreSQL archived aggregates remain authoritative. This is a snapshot tool, not a promise of infinite raw retention or a completed PG-only migration. Backup row/byte bounds, key compatibility and precise validation are documented in ACCEPTANCE_HISTORY_STORE.md. The new history interfaces require their own application and Docker validation; earlier bf77 images do not contain them.
