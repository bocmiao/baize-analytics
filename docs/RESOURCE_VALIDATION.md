# 资源与负载测量说明

本页说明一次有限负载下的正确性、恢复和资源观察，不是服务器容量或延迟承诺。被测软件为 `ae0e55fdd5458b422a8e660faddef70b4b6353fd`；测量摘要记录的文档版本为 `8e0e5cc29f6728598e411c36923dcaba69781323`。后续文档修改不代表重新构建了软件。

数据依据为随验收资料交付的 `constrained-profile/final-summary.json` 和 `independent-actual-review.json`；独立核验检查了原始计数、资源限制及证据文件哈希。

## 测量条件

标准版使用独立 PostgreSQL/Redis，Lite 使用本地 SQLite；未启用 ClickHouse 或外部模型。两者顺序运行相同合成流量，发送端使用 HTTP 新连接而非长连接复用，并计划每 10 秒发起一次并发统计查询：

- 每批 50 个事件；最多 2 个并发请求，发送端等待队列最多 8 批。
- 固定阶段：每秒安排 1 批，共 1,000 个事件，目标输入为 **50 events/s**。
- 峰值阶段：每 100ms 安排 1 批，共 500 个事件，目标输入为 **500 offered events/s**。这是发送计划，不是持续接收或处理速度。
- 负载后对应用进程执行 SIGKILL，再启动应用；先等待健康恢复，再等待统计覆盖完整和积压排空。
- 重投既有 100 个事件 ID，随后查询并核对全部 1,500 个唯一 ID；重投不增加计数。最终两者均为 PV 1,500、UV 150、会话 150、覆盖率 1。

CPU/内存限制由容器配置和实际 cgroup 文件双重核对，禁用 swap：

| profile | 服务额度 | 合计 |
| --- | --- | --- |
| 标准版 | app：0.60 CPU / 1.0 GB；PG：0.35 CPU / 0.7 GB；Redis：0.05 CPU / 0.1 GB | 1 CPU / 1.8 GB |
| Lite | app：1 CPU / 2.0 GB | 1 CPU / 2.0 GB |

GB 为十进制。上述合计只覆盖列出的服务，不含宿主 OS、Docker daemon、发送端及可选服务；**不能当作整台物理 1C2G 机器认证**。标准版各服务静态额度不能借用彼此闲置的 CPU；观测用 `docker exec` 的 CPU 开销包含在服务计数中。

## 实际结果

ACK 延迟是每批 HTTP 接收响应耗时，不能代替后台聚合完成耗时。

| 项目 | 标准版 | Lite |
| --- | ---: | ---: |
| 固定阶段 ACK P95 | 1,281.84 ms | 145.49 ms |
| 峰值阶段 ACK P95 | 3,376.88 ms | 39.85 ms |
| 峰值阶段全部请求完成时间 | 9.12 s | 0.94 s |
| 首次健康就绪 | 2.10 s | 0.62 s |
| SIGKILL 后健康恢复 | 1.83 s | 0.89 s |
| 健康恢复后统计排空 | 62.59 s | 0.08 s |
| 恢复并排空后 20 次查询 P95 | 78.58 ms | 95.37 ms |
| 观察窗口内 `memory.current` 快照和最大值 | 600,530,944 B | 254,443,520 B |

两者收到全部固定及峰值批次，没有未发送批次或采集拒绝；标准版峰值发送队列达到 8 批。因此，标准版这一轮不能描述为持续处理 500 events/s。标准版最终 dirty/尝试积压为零；Lite 最终无待处理任务，WAL dirty bytes 为零。

健康恢复只说明服务能响应；统计排空才说明本数据集完成恢复后的聚合。SIGKILL 对应退出码 137，记录的 `oomKilled` 为 false；观察到的 OOM 计数也为零，不等于任意负载都不会 OOM。

查询分组必须分开解释：标准版负载期间仅记录 2 次查询，P95 为 2,702.42ms；排空轮询最大耗时为 5,897.05ms。Lite 负载期间仅 1 次查询。恢复后的 20 次查询不能掩盖这些耗时，小样本也不能证明生产 SLO。

内存数值包含阶段转换处的额外快照，各服务在快照内依次读取；它们不是严格同时或连续峰值，也不等于所有进程 RSS。Lite 最大值来自 SIGKILL 前额外快照，定期采样文件单独的最大值较小；内核峰值与计数分别保留在各重启阶段。

磁盘方面，标准版 PG 总增长 299,816,100 B，**其中已包含** WAL 增长 184,549,376 B，不能重复相加；Redis 增长 100,048 B。Lite 应用目录增长 2,934,536 B。实际磁盘日志字节不可读，记录为未知而不是零。这些短窗口数据不能线性外推每天的磁盘容量。

## 容量与交付边界

- 本轮证明的是有限 1,500 事件夹具的持久计数、重试去重、恢复与已施加服务额度。没有证明持续混合写入/删除、单大站点、百万事件/日或物理 1C2G 的长期容量。
- 历史严格 ClickHouse `5000` 负载验收未通过；本页没有重跑或替代该项，也不将较小 PG/Lite 结果作为严格模式通过证明。更完整状态见 [项目状态](STATUS.md) 与 [历史实现证据](IMPLEMENTATION_CHECKLIST.md)。
- 完整 `tracker.js.gz` 的交付体积为 **4,998 B**。这是独立的追踪脚本体积指标，与后台吞吐、服务内存和容量结论分开。

## 共享总额度对照：同软件实际结果

标准版另用相同 `ae0e55f` 应用和同一流量夹具，把 app、PostgreSQL 17.11、Redis 7.4.11 放在**同一个真实 cgroup**，共同使用 1 CPU / 1.8 GB、swap 为零。PG 的 `fsync`、`synchronous_commit`、`full_page_writes`、JIT 均为 on；未用关闭耐久性或数据库功能来换取延迟。

| 项目 | 静态服务分额 | 共享总额度 |
| --- | ---: | ---: |
| 固定阶段 ACK P95 | 1,281.844 ms | 603.759 ms |
| 峰值阶段 ACK P95 | 3,376.878 ms | 1,567.767 ms |
| 应用被杀后统计排空 | 62.589 s | 66.724 s |
| 观察到的 `memory.current` 最大值 | 600,530,944 B，服务依次读取后求和 | 849,649,664 B，单一 cgroup 直接读取 |

共享对照最终核实 1,500 个唯一 ID、PV 1,500、UV 150、会话 150、覆盖率 1，积压为零。ACK 延迟较小，但排空未变快；仍不能据峰值输入计划声称持续处理 500 events/s。内存两列的测量口径不同，不能把它们当作相同采样方法下的精确差值。

共享拓扑还执行了**整个服务容器**的 SIGKILL，包含 app、PG 和 Redis。退出码为 137，`oomKilled=false`，健康恢复为 2.594s，之后再次核实 PV 1,500、覆盖率 1；重投既有 100 个事件不增加唯一计数。这是进程/容器崩溃恢复，**不是物理断电或宿主磁盘故障测试**。应用单独重启不清空共享 cgroup 计数，整个容器重启后的计数另按新阶段记录。

观测方式也改变了：静态分额每次观察分别执行 3 次 `docker exec`，共享组只需 1 次。没有逐请求队列等待时间或数据库调用分段计时；这些结果不能单独证明 PG 额度切分导致某个延迟，也不能独断数据库或采集器的因果关系。共同服务额度仍排除宿主 OS、Docker daemon 和发送端，不是物理整机 1C2G 认证。

共享结果依据为随验收资料交付的 `shared-standard/shared-comparison-summary.json` 与更新后的测量摘要。上述表格只对应未修改的 `ae0e55f`；候选采集器的变更后测量见下一节，不能把两组软件混为同一发布版本。

## 窄采集优化：候选源码实际对照

候选改动只针对同一事件的重复 identity 查询：非 `identify` 事件复用该事件已经检查的结果；`identify` 修改身份后仍重新检查。结果不跨事件缓存，同站点事务 gate 保持，HTTP 202 仍在 COMMIT 完成后返回。

匿名 pageview 的 50 事件批次，显式 SQL 调用计数约从 462 降到 362。该源码计数含事务等额外调用，不是数据库逐调用耗时分解，也不能直接推导延迟收益。相关真实 PG 验证为 10 项通过，另 14 项因未选择而跳过；这不是完整测试套件。

相同流量夹具与共享 1 CPU / 1.8 GB 条件下：

| 项目 | 未修改 ae0 基线 | 候选采集器 |
| --- | ---: | ---: |
| 固定阶段 ACK P95 | 603.759 ms | 499.837 ms（降低约 17.2%） |
| 峰值阶段 ACK P95 | 1,567.767 ms | 2,092.262 ms（增加约 33.5%） |
| 应用被杀后统计排空 | 66.724 s | 65.407 s |
| 整个服务容器被杀后健康恢复 | 2.594 s | 2.340 s |

结果是混合的：固定阶段变快，峰值阶段变慢，不能描述为全面提速。候选同样核实 1,500 个唯一事件、PV 1,500、覆盖率 1；重投 100 个既有事件没有新增唯一计数。整个容器中的 app、PG、Redis 被 SIGKILL，退出 137 且非 OOM；健康探测期间的连接重置保留在记录中。这仍不是物理断电测试。

本次 after 测量使用基线镜像加只读候选编译模块，证据为 `shared-standard-after/result.json` 与 `actual-overlay-collect-witness.json`。候选 `src/server/collect.ts` SHA256 为 `987f121cf75cbbb5a8c9d7523a705170f88a72a26e263ff398a9a4f165cab41f`；实际执行的 `collect.js` SHA256 为 `bc31aea4fc43bbd72320f03904ed09360eb7dd9600008809e928691d57a6664f`。

候选测量不是旧 `ae0e55f` 正式镜像的新功能验收。最终发布须由发布清单的完整软件 SHA、源码文件哈希及实际编译文件哈希另行绑定；只有输入匹配才能引用这里的结果，正式产物启动与完整性验证也需单独记录。
