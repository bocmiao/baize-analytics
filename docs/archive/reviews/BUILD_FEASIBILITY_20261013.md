# 构建空间复核与本轮收益（2026-10-13）

> 历史记录：本文的“当前／最新”、测试结果与下载信息仅指其日期和版本。当前入口见 [项目状态](../../STATUS.md)；原路径映射见 [归档索引](../README.md)。原始失败、未测项及证据保留。

本轮只执行磁盘、Docker/cache/旧镜像元数据和源码输入检查，没有启动构建、安装或生产操作。软件代码保持 `129d972`；已存归档的字节和版本未改写。详细测量与假设见 [LOW_PEAK_BUILD_FEASIBILITY.json](../../validation/performance-20261013/LOW_PEAK_BUILD_FEASIBILITY.json)。

## 仍不能安全构建的原因

实测 `/workspace` 可用 2,248,790,016B，保护值固定 2,147,483,648B，余量仅 101,306,368B（96.61MiB）。Docker root 是 `/var/lib/docker`，驱动 vfs。[Docker 官方说明](https://docs.docker.com/engine/storage/drivers/vfs-driver/)明确 vfs 无写时复制，新层会深拷贝父层；因此几 MB 的改动也可能新增一个完整文件树，不能把 `docker system df` 的逻辑层增量当成磁盘峰值。

旧 Lite/标准镜像的实际逻辑层大小分别为 361,560,007B / 389,908,073B；其 runtime COPY payload 分别 131,585,249B / 159,933,315B。相同锁定依赖的 Lite 生产 node_modules 仅常规文件已经 124,480,209B，超过现有96.61MiB余量。即便完全跳过构建缓存增长，按既有 Lite 全树物化参考也还差约248.20MiB；这个数字只说明一次最终物化的缺口，绝不是完整构建所需空间。

可行的减量办法已经按源码核对，但都不足以跨过当前最低缺口：

- 只排除历史 ZIP 仅省53,505B。排除全部 docs/tests/托管元数据、保留源码、构建输入和 runtime-stage 所需目录，候选输入可从69,388,709B降到5,135,840B（66.18→4.90MiB）。源 checkout、文档与截图仍保留；运行包发布器仍从同一固定Git revision导出文档，不改同源验证。没有实际运行这个候选上下文。
- 先标准再Lite可复用相同依赖和COPY输入缓存、减少同时运行峰值；但不删除旧缓存时新增文件树仍会累计，不能把顺序构建等同于回收空间。352MB npm-ci缓存只有在基础digest、包/lock及构建输入匹配时才可复用；不使用旧应用镜像充当优化版基底。
- 标准版合并 build 与 runtime staging 的两个RUN可少一次重复builder快照。这只是未来可选方案，本轮未修改Dockerfile；当前余量连最小产物物化也不足，不能为让预检过关先改构建输入或降低保护值。
- `/tmp`剩约4.63GiB，但它是tmpfs；已有归档写在那里。把上下文/归档写到/tmp不等于迁移Docker层存储，最终镜像导入原vfs仍受限；没有修改daemon、权限或新增资源。

按既有cache大小、精简上下文、vfs完整树复制及共用缓存模型，两版保留的新快照/最终树预算约3,431,610,872B，比当前保护值以上余量多3,330,304,504B（3.10GiB）。这是保守规划模型，非新构建实测峰值：取整cache增量、Lite prune未扣减、尚未计inode/导出暂存等差异。旧四原生包展开实际占958,996,480B，两份旧离线save压缩文件共422,448,079B；发布器还会产生临时容器/暂存。完整交付规划建议**额外6GiB可用构建盘**，先重新测量再逐步执行，不保证此空间必然完成。

停止点明确：没有开始新Dockerfile构建；没有删除旧证据/包/卷，没有prune，没有放松2GiB保护或改权限，也没有重试Library。无法在保护值下安全实测最终峰值，就不能声称“精简后已能构建”。

## 三条普通用户可理解的收益

1. **切换图表少重复初始化。** 六次面板切换的实例数7→1；同帧50次resize合并为1次。前期比较初次请求2→1（固定HTTP浏览器fixture）；标准版实际下载页进入和刷新各1个content请求。说明重复工作减少，不宣称已测出FPS或所有设备都更流畅。Lite实际不开放下载content报表。
2. **带筛选/半小时范围的报表少重复查数据库。** 同一真实PG请求内 numeric scan 2→1，SQL 58→51或48→41；对齐范围仍51不变。PV、UV、覆盖率一致；没有跨请求缓存，也不把混合的单次查询耗时当加速承诺。

## 历史混合结论与未解决项

历史RESOURCE_VALIDATION的相同旧夹具：固定20批×50、每秒一批（50 offered events/s）；峰值10批×50、每100ms一批（500 offered events/s）；最多2个并发请求、排队8批，计划每10秒并发统计查询，发送器在服务cgroup外。标准共享组的旧窄采集优化固定603.759→499.837ms，峰值1567.767→2092.262ms，仍是**固定变快、峰值变慢**。旧Lite初始实验为2.0GB，不能拿来当本轮1.8GB的同条件基线。

本轮固定阶段的发送计划是500而非历史50 offered events/s；新三波每轮1500事件而非历史峰值500，发送器/并发控制/查询计划及源码也不同。不能用本轮3389ms与历史500ms推导变慢倍数，也不能拿本轮三波改善改写历史峰值退化。另一个本轮30请求同时发送的诊断出现204过滤，基线实际接收1450、优化1400，工作量不同，排除在改善表之外；它不是历史资源报告的峰值阶段。历史报告末尾曾将峰值简称为“旧单波”，本次仅纠正文档用词，历史数据不改。

未解决重点：标准ACK仍为秒级，500ms目标未通过；逐事件page_path SQL及队列/事实发布成本仍在，未默认开启已有batch开关或开发新算法。24性能对照早于最后分区安全修复，不宣称最终DDL变体重测过延迟。新镜像/四原生包/离线save及Library下载继续阻塞；生产、真实宝塔、跨平台、物理断电/存储故障及整台1C2G长期容量未验证。旧5000容量测试未重跑，tracker4998B gzip是独立体积指标。
